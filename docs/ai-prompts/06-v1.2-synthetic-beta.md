## 1. Synthetic Beta의 정직한 정의

가상 테스터는 AI가 설정한 **서로 다른 목표·사용 습관·기기·제약을 가진 평가 관점**이다. 실제 참여자를 모집한 사용자 연구가 아니다.

1. 실제 앱에서 수행한 행동과 그 결과, 코드/테스트로 확인한 규칙, 가상 사용자의 예상 해석을 구분한다.
2. “초보자가 버튼을 찾기 어려워할 수 있다”는 설계 가설이다. “모바일 320px에서 버튼이 가려져 눌리지 않았다”는 재현 가능한 관찰이다.
3. 실제로 실행하지 않은 행동·발화·인터뷰·만족도·과업 시간·사용자 성공률을 만들지 않는다.
4. 자동화 실행 시간은 사람의 과업 수행 시간이 아니다. 페르소나별 점수 평균도 사용자 만족도가 아니다.
5. 가상 테스터의 검토 의견만으로 기능 PASS를 선언하지 않는다. 기능 판정에는 실제 조작·단언·저장 결과 등 근거가 필요하다.
6. 동일 모델의 역할 전환을 여러 독립 모델·사람의 평가로 표현하지 않는다.
7. 도구가 지원되면 관점별 검토를 별도 에이전트에 맡길 수 있다. 변경 담당은 통합하여 파일 충돌을 방지하고, 사용한 방식과 한계를 기록한다. 에이전트가 없어도 한 세션에서 관점을 분리해 계속 진행한다.
8. 실제 휴대폰·OS 한글 IME·스크린 리더를 쓰지 않았다면 해당 항목을 에뮬레이션/이벤트 검증과 구분한다.

## 2. 기준점·호환성·작업 환경

먼저 적용되는 AGENTS.md, 현재 브랜치·작업 트리·remote·태그·패키지·개발 문서·CI·배포 방식을 확인하라. 사용자 변경이 있으면 보존한다. 다른 실습 폴더를 변경하지 않는다.

README.md, CHANGELOG.md, docs/product-spec.md, docs/decisions.md, docs/V1_1_UPDATE.md, docs/validation.md, docs/deployment.md, AI 활용 기록과 실제 테스트를 읽어 현재 제품 규칙을 파악하라. 현재 구현이 명세와 다른 부분을 무조건 정답으로 취급하지 마라.

- 실제 시작 커밋·앱 버전·v1.1.0 태그 위치를 기록한다.
- v1.1 문서·스크린샷·증거와 기존 태그를 보존한다.
- 기존 검사와 테스트를 실행해 baseline 결과를 기록한다. 실패가 있으면 변경 전 실패와 이번 변경으로 생긴 실패를 구분한다.
- 테스트는 격리된 브라우저 context와 합성 데이터로 수행한다. 사용자의 실제 목록·브라우저 프로필을 초기화하거나 교체하지 않는다.
- 앱 버전과 저장 스키마 버전은 별개다. 기본적으로 앱은 1.2.0, 저장 키 focusday:v1과 데이터 version:1은 유지한다.
- 예전 데이터의 모든 필드·id·완료·예시 상태가 유지되어야 한다. 첫 렌더에서 빈 목록을 저장하지 않는다.
- 데스크톱 노트북의 시연 경로를 우선 확보하고 모바일을 함께 확인한다.

각 유형별로 “핵심 과업 1개 + 관련 실패/복구 과업 1개 이상”의 연결된 세션을 실제 실행한다. 동일한 공통 검사를 12번 복제하여 건수만 늘리지 마라. 공통 검사는 대표 환경에서 수행하고, 기기·입력 방식·제약에 따라 결과가 달라질 수 있는 검사는 해당 환경에서 다시 수행한다.

가상 초보자의 버튼 발견이나 혼동은 AI 관점의 walkthrough로 기록한다. 자동화가 버튼을 즉시 찾았다는 사실을 사람의 발견 용이성으로 해석하지 않는다.

## 4. 데이터·기기·날짜 조건

테스트 fixture는 실제 생성 규칙과 같은 스키마를 사용한다. 기본 과업은 UI에서 데이터를 만들고, 날짜·손상·대량·저장 실패 재현은 격리된 테스트 환경에서만 주입한다. fixture 주입을 실제 UI 입력 검증으로 대체하지 않는다.

### 데이터

- 빈 목록, 예시 목록, 사용자/예시 혼합.
- 서로 다른 id의 같은 제목, 같은 id의 같은 내용/다른 내용.
- 오늘 집중, 어제 집중, 이틀 전 집중, 기한 없음, 미래 기한, 오늘 기한, 기한 초과.
- 위 조건이 중첩된 항목과 완료된 항목.
- 높은/보통/낮은/없는 우선순위, 없는/짧은/24자 분류.
- 한글·영문·숫자·이모지·구두점, 앞뒤 공백, 긴 단어, 줄바꿈이 있는 상세 제목.
- 0개·1개·50개·200개를 실제 목록 과업에 사용한다.
- 대량 백업 경계는 별도 데이터 검사로 수행한다. 6,000개 데이터 검사를 정상 목록의 사용성 평가와 혼동하지 않는다.

### 환경

- 1440×900, 1366×768, 390×844, 320×740.
- 모바일 touch와 390×480의 축소 가시 영역.
- 200% 브라우저 확대 또는 도구에서 지원하는 동등 조건. 지원하지 않으면 다른 종류의 확대라고 명시한다.
- Asia/Seoul을 기본으로 하고 날짜 규칙은 America/New_York에서도 확인한다.
- 로컬 어제, 자정, 월말·연말, 윤년 및 DST 경계 중 해당 규칙에 필요한 경우.
- 실행 브라우저 이름·버전, 실제 기기/에뮬레이션, viewport, 테스트 시각·시간대를 기록한다.

## 5. 세부 행동 체크리스트

아래 항목은 평가 범위다. 이미 있는 테스트가 충분한 근거를 제공하면 재사용하되 결과와 근거 위치를 연결한다. 단위 테스트 PASS만으로 대응 UI 동작을 PASS 처리하지 마라.

### A. 빠른 입력과 Enter

| ID | 실제 행동 | 확인 기준 |
|---|---|---|
| A01 | 빈 앱에 진입하고 입력 시작 | 시작 안내, 입력 이름/placeholder, 입력 가능한 상태가 명확하다. |
| A02 | 오늘에서 “자료구조 과제 제출”을 입력하고 Enter 1회 | 항목 1개만 생성, 제목 정확, focusDate=오늘, dueDate=null, 오늘/전체 숫자 갱신. |
| A03 | 전체에서 “주말 장보기”를 입력하고 Enter | 항목 1개 생성, focusDate=null, 기한 없음. 오늘에 자동 배정하지 않는다. |
| A04 | 5개 제목을 연속으로 입력하고 각각 Enter | 이전 제목이 남지 않고 입력 포커스가 유지되며, 각 제출이 1개씩 생성된다. 새로고침 후 유지. |
| A05 | 같은 조건에서 추가 버튼과 Enter를 각각 사용 | 두 경로의 생성 규칙·기본값·피드백이 같다. 서로 다른 항목의 id·시각은 같을 필요 없다. |
| A06 | 빈 문자열/공백만 입력한 뒤 Enter와 추가 | 빈 항목을 만들지 않는다. 안내와 포커스가 합리적이며 복구 후 정상 입력된다. |
| A07 | 앞뒤 공백이 있는 제목 제출 | 명세에 맞게 공백 정리, 내부 글자·띄어쓰기 보존, 저장/검색 결과 일치. |
| A08 | 199자·200자·201자 입력/붙여넣기 | 한도를 넘는 데이터가 저장되지 않는다. 입력 차단·정리·오류 방식이 실제 UI와 문서에 일치한다. |
| A09 | 제출 직후 Enter를 다시 누르거나 빠르게 추가/Enter | 처리 완료된 같은 입력의 중복 제출·빈 항목을 방지한다. 같은 제목을 새로 입력한 의도적 별도 항목은 허용한다. |
| A10 | 한글 조합 중 Enter, 조합 완료 후 제출 | 조합 확정 Enter로 의도하지 않은 추가가 발생하지 않는다. 완료 후 정상 제출은 1회만 처리된다. OS IME 미실행은 별도 표기. |
| A11 | 제목 입력 중 N·/·Escape, 검색 중 Enter | 전역 단축키가 입력을 가로채지 않는다. 검색 Enter가 새 항목을 생성하지 않는다. |
| A12 | 모바일 입력의 Enter/완료/이동 조건 | 지원되는 실제/에뮬레이션 조건에서 결과 확인. 가상 키보드를 직접 쓰지 않았다면 실제 기기 검증으로 기록하지 않는다. |

“일정 입력 후 Enter”의 기본 기준은 **할 일 제목을 입력하면 빠르게 추가되는 흐름**이다. “내일 오후 3시”를 제목에 썼다고 기한을 자동 파싱하는 기능이 있다고 가정하지 마라. 자연어 파싱은 이번 범위에 추가하지 않는다.

### B. 상세 편집·기한·우선순위·분류

| ID | 실제 행동 | 확인 기준 |
|---|---|---|
| B01 | 제목을 눌러 상세 편집 열기 | 현재 값 정확, 제목에 초기 포커스, 읽기/편집 관계 명확. |

## 6. 반드시 재현·보완할 백업 경계 문제

앞선 코드 검토에서 다음 **순수 데이터 경로**가 재현됐다. 현재 checkout에서도 먼저 다시 확인하라.

- 스키마에 맞는 항목 6,000개.
- 각 title은 한글 “가” 200자, id는 서로 다름.
- createdAt/updatedAt은 유효한 ISO timestamp.
- dueDate/focusDate/category/completedAt=null, priority=none, isDemo=false.
- 기존 createBackup 결과를 UI처럼 들여쓰기 JSON으로 직렬화하면 약 5.31MiB였다.
- 기존 parseBackup의 5MiB 제한 때문에 앱이 만든 파일을 다시 읽지 못했다.

수치는 필드 값과 직렬화 방식에 따라 변하므로 실제 fixture·bytes를 다시 기록한다. 이 재현은 실제 브라우저 저장 quota 통과나 6,000개 UI 성능을 검증했다는 뜻이 아니다.

목표는 “백업 다운로드 성공”과 “이 앱에서 복원 가능”의 차이를 해결하는 것이다.

1. 최소한 내보내기 전에 실제 UTF-8 byte 크기를 검사한다.
2. 불필요한 들여쓰기 제거 등 작은 변경으로 해결 가능한 범위를 먼저 확인한다.
3. 앱이 허용하는 전체 데이터와 가져오기 제한의 일관성을 검토한다.
4. 여전히 자체 백업을 복원할 수 없는 범위가 있으면, 제한을 안전하게 조정하거나 복원 가능한 보존 경로를 마련하고 이유·메모리/파일 처리 범위를 검증한다.
5. 데이터 자르기·일부 항목 누락·완료/예시 제외·무제한 파일 허용으로 해결하지 않는다.
6. 경고만 추가했다면 “제한 안내 개선”으로 기록하고 round trip 문제까지 해결했다고 주장하지 않는다.
7. 기존 정식 백업 형식과 기존 파일 호환성을 유지한다. 불필요한 압축 라이브러리·대규모 파일 관리 UI를 도입하지 않는다.
8. 실제 지원하는 크기 경계와 내보내기→다시 가져오기 회귀 테스트를 추가한다.

## 7. 관찰 기록과 문제 판정

각 평가 항목은 다음을 기록한다.

- Case ID / Persona ID / 실행 시각 / 기준 커밋.
- 환경·viewport·입력 방식·시간대.
- 초기 상태와 fixture 식별자.
- 재현 가능한 행동 순서.
- 명세와 제품 규칙에 따른 기대 결과.
- 실제 관찰 결과와 최종 데이터/저장 값.
- 상태: PASS / FAIL / INCONCLUSIVE / NOT_RUN.
- 근거 종류: 실제 브라우저 조작 / 자동화 E2E / 순수 규칙·데이터 테스트 / 코드 검토 / AI walkthrough 가설.
- 근거 파일·테스트명·스크린샷/trace·필요한 경우 오류 로그.
- 발견 이슈 ID와 수정/재검증 연결.

문제를 다음 우선순위로 분류한다.

- P0: 데이터 손실·원본 덮어쓰기·핵심 복구 불능.
- P1: 정상 입력/저장/계획/복원의 핵심 과업을 막거나 잘못 적용.
- P2: 재현 가능한 모바일·키보드·피드백·탐색 문제와 비핵심 경계 결함.
- P3: 의미 이해에 영향을 주는 문구·시각적 일관성 개선.

심각도는 사용자 영향과 재현 조건으로 설명한다. 스타일 선호만으로 결함을 만들지 않는다. 가상 관점의 혼동 가설은 객관적 기능 실패와 별도 표시한다.

문제는 “관찰 → 원인 → 변경 → 재검증”으로 연결한다. 발견한 원본 실패 증거를 수정 후 성공 자료로 덮어쓰지 않는다.

## 8. 개선 범위와 구현 원칙

- P0/P1을 먼저 해결하고, P2는 이번 핵심 과업과 관련된 범위에서 해결한다.
- 가상 관점의 UX 가설은 실제 UI 근거와 개선 이유가 충분한 경우에 반영한다. 판단이 필요한 사안은 선택 이유와 남은 불확실성을 기록한다.
- 오늘/전체 두 최상위 보기, 제목 중심 빠른 입력, 기한/집중 분리, 수동 어제 이어가기, 사실 기반 후보, 선택형 예시, 저장 보호를 유지한다.
- Enter를 모든 입력의 “저장”으로 일괄 변경하지 않는다. textarea 줄바꿈, 한글 조합 확정, 버튼 활성화, 빠른 입력 제출은 맥락이 다르다.
- 동일 제목의 의도적 별도 할 일을 금지하지 않는다.
- 개선에 꼭 필요한 작은 도움말·레이블·포커스·스크롤·배치·오류 복구는 구현한다.
- 로그인·서버·동기화·캘린더·반복·알림·자연어 날짜 파싱·포모도로·하위 작업·테마·앱 내부 AI는 자동으로 추가하지 않는다.
- 전면 디자인 교체나 의존성 추가는 기본 해법으로 사용하지 않는다.
- 테스트 결과에 맞추려고 기존 기대값을 완화하지 않는다. 의도적 제품 규칙 변경이 필요하면 근거와 문서를 함께 수정한다.
- 버전 숫자를 채우기 위해 개선 개수·커밋 개수·테스트 개수·점수 목표를 만들어 맞추지 않는다.
- 실제로 확정된 개선이 없는 항목은 미변경 또는 후속 검증 대상으로 기록한다.

## 9. 구현·재검증 절차

1. 현재 v1.1 baseline과 검사 결과 보존.
2. 공통 체크리스트 및 12개 유형의 세션 설계·실제 실행.
3. 초기 발견 보고서와 수정 우선순위 확정.
4. 재현된 기능 실패와 결정한 UX 개선 구현.
5. 수정한 문제에 필요한 회귀 테스트 추가. 이미 충분한 검사는 재사용한다.
6. 수정 항목과 영향받는 관련 과업을 재실행하고 변경 전후 근거 비교.
7. 타입·lint·단위·시간대·production build·기존 E2E와 새 회귀 검사 실행.
8. 실제 Pages 하위 경로 /focusday/에서 production 동작 확인.
9. GitHub 반영·CI·배포 후 공개 사이트에서 주요 과업 재검증.

기존 테스트 개수는 baseline에서 직접 확인한다. v1.1 기록에는 단위 42개·날짜 각 22개·E2E 55개가 있으나, 현재 코드의 실제 수와 결과를 기준으로 보고한다.

한 번 통과한 검사를 근거 없이 반복하지 않는다. 추가 변경·실패·환경 차이로 필요한 범위만 재검증하고 최종 필수 검사를 완료한다. 도구 오류·브라우저 설치 실패·다운로드 수신 실패는 앱 결함과 구분한다.

실행할 수 없는 검사는 NOT_RUN 또는 INCONCLUSIVE로 남긴다. 브라우저가 없으면 가능한 코드·순수 규칙 검증과 구현·문서화를 계속하되, 실제 UI 평가 완료를 주장하지 않는다.

기능 검증 결과와 UX 가설을 별도 표로 제시한다. “가상 사용자 12명 모두 만족”, “시간 30% 감소”, “사용성 95점” 같은 측정하지 않은 결론을 작성하지 않는다. 스크린샷에 테스트 데이터를 사용했음을 표시하고, 실제 화면과 목업을 구분한다.

## 11. GitHub·버전·배포

- 기존 v1.0.0/v1.1.0 태그와 commit을 이동하거나 삭제하지 않는다.
- 평가 설계·재현/테스트·실제 개선·최종 검증/문서 등 실제 완료 작업별로 의미 있는 커밋을 만든다.
- 사용자의 기존 Git identity·remote·인증을 활용한다. 다른 저장소를 만들거나 force push하지 않는다.
- 구현·필수 검증이 완료된 실제 v1.2.0 결과에 출시 태그를 추가하고 정상 push한다.
- 기존 CI와 Pages workflow를 사용한다. 기존 정책상 Pages 배포 ref는 허용된 main을 사용하고, 배포 실패를 피하려고 환경 보호 규칙을 바꾸지 않는다.
- 배포 소스 commit·태그·최신 main 관계를 기록한다. 문서 후속 커밋만 차이가 있으면 그 사실을 설명한다.
- CI 성공과 배포 완료를 실제 원격 상태로 확인한다. 공개 사이트의 버전·자산·핵심 입력·계획·모바일·백업 경로를 확인한다.
- 권한이나 도구가 막히면 완료된 로컬 결과와 정확한 미완료 단계를 제공한다. push/배포를 시도한 것만으로 성공이라 기록하지 않는다.

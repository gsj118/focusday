첨부한 `deep-research-report.md`를 설계 근거로 사용하여, 개인용 할 일 관리 애플리케이션을 실제로 구현·검증·문서화하라. 계획이나 코드 예시만 제시하지 말고 현재 작업 공간에 실행 가능한 프로젝트를 완성하라.

너는 제품 설계, 프런트엔드 개발, UX 검토, 테스트, 기술 문서화를 담당한다. 아래 명세 안에서 세부 구현을 자율적으로 결정하고, 발견한 결함은 수정 후 재검증하라.

## 1. 과제와 완성 목표

- 대학 ‘인공지능활용실습’ 과제이며, 프로젝트 전체를 GitHub에 공유하여 결과물과 개발 과정을 보여준다.
- 오늘 안에 구현·검증·문서화를 마치는 시연용 프로토타입이다. 판단 기준은 기능 수보다 제품 경험의 완결성이다.
- 교수님이 노트북에서 직접 시험할 수 있어야 하며, 모바일에서도 실제 사용 가능한 반응형 UI를 제공한다.
- 주 사용자는 할 일을 자주 떠올리지만 복잡한 관리 체계와 많은 설정을 유지하고 싶지 않은 개인 사용자이다. 이는 리서치에 근거한 설계 가설로 기록한다.
- 앱 이름은 `Focusday`, 핵심 가치는 “생각난 일은 빠르게 담고, 오늘 할 일만 선명하게.”로 정한다.
- UI와 핵심 문서는 자연스러운 한국어로 작성한다.
- AI 활용은 리서치 해석 → 설계 결정 → 구현 → 검토 → 실제 검증 → 문서화의 연결 과정으로 입증한다. 앱 내부 AI 기능은 구현하지 않는다.

먼저 리서치 원문과 현재 폴더, Git 상태, 기존 프로젝트, 적용되는 AGENTS.md를 확인하라. 리서치가 없다면 우선 아래 명세로 진행하고 원문 미확인 사실을 기록하라. 충돌 시 이 프롬프트의 명시적 지시를 우선하며, 중요한 해석은 `docs/decisions.md`에 남긴다. 기존 사용자 파일과 다른 실습 폴더를 보존하라.

## 2. 기술과 범위

기본 기술은 React + TypeScript + Vite + 일반 CSS + localStorage이다. 서버 없는 단일 페이지 웹앱으로 구현한다.

- 라우터, 전역 상태 라이브러리, UI 프레임워크, DB, 인증은 사용하지 않는다.
- 컴포넌트, 도메인 로직, 저장 어댑터는 이해하기 쉬운 수준으로 분리한다. 과도한 추상화는 피한다.
- 개발 의존성은 필요한 테스트·린트 도구만 추가하고 lockfile을 포함한다.
- 외부 웹폰트, 유료 API, API 키 없이 실행되어야 한다.
- 실제 설치 가능한 호환 버전을 확인한다. 버전 번호와 라이브러리 API를 추측하지 않는다.
- GitHub Pages에서 정적 배포할 수 있게 구성하되 저장소 경로와 기존 배포 설정을 확인한다.

최종 필수 기능:
빠른 입력, 오늘/전체 보기, 오늘에 추가·제거, 기한, 제목·속성 편집, 우선순위, 단일 분류, 완료·미완료 복원, 삭제와 실행 취소, 로컬 저장, 검색, 선택형 예시 데이터, 반응형 화면, 빈 상태·오류 상태, 키보드 접근성.

핵심 CRUD와 저장·날짜 규칙을 먼저 검증한 뒤 검색·예시 데이터·시각적 완성도를 추가하라.

제외 기능:
로그인, 서버, 클라우드 동기화, 협업·공유, 캘린더, 시간별 일정, 반복 작업, 알림, 하위 작업, 메모·첨부, 습관, 포모도로, 게임화, 앱 내부 AI, 음성·자연어 파서, 드래그앤드롭, 대량 편집, 테마·다크 모드, PWA.

## 3. 데이터와 화면 규칙

저장 구조:
`AppData = { version: 1, tasks: Task[] }`

Task 필드:
`id, title, createdAt, updatedAt, dueDate, focusDate, priority, category, completedAt, isDemo`

- id는 고유 문자열.
- title은 trim 후 공백만 있는 입력을 거부하고 최대 200자로 제한.
- createdAt, updatedAt, completedAt은 ISO timestamp. 미완료 completedAt은 null.
- dueDate, focusDate는 로컬 달력 날짜 `YYYY-MM-DD | null`.
- priority는 `none | low | medium | high`, UI는 `없음 / 낮음 / 보통 / 높음`.
- category는 선택적인 짧은 문자열 한 개. 별도 분류 관리 화면은 만들지 않는다.
- isDemo는 boolean이며 일반 사용자가 생성한 항목은 항상 false.

기본 진입 화면은 `오늘`. 최상위 탐색은 `오늘 / 전체` 두 개만 둔다.

오늘의 미완료 항목:
`focusDate === today OR dueDate === today OR dueDate < today`
단, 날짜 비교는 null을 제외한 유효한 날짜에만 적용한다.

- 오늘에는 `기한 초과`와 `오늘` 섹션을 제공하며 중복 표시하지 않는다.
- 전체에는 모든 미완료 항목을 제공한다.
- 완료 항목은 전체 화면의 접을 수 있는 `완료된 할 일` 영역에 제공한다. 완료 후 피드백에서도 해당 영역으로 이동할 수 있게 한다.
- 검색은 현재 보기의 제목·분류에 대소문자 구분 없는 부분 문자열 검색을 적용한다. 전체 보기에서는 완료 영역도 검색 대상에 포함한다.
- 메뉴의 개수는 각 보기의 미완료 수, 검색 결과 수는 현재 검색 결과로 구분한다.

`오늘에 추가`는 focusDate만 오늘로 설정하고 dueDate를 바꾸지 않는다.
`오늘에서 빼기`는 focusDate만 null로 바꾼다.
기한이 오늘 또는 과거이면 focusDate를 지워도 오늘에 남는다. 이 경우 “기한 때문에 오늘에도 표시됩니다”라는 짧은 안내를 제공하고 기한 편집으로 연결한다. 사라지는 것처럼 오해하게 만들지 않는다.

빠른 입력의 기본값:
- 오늘 화면에서 생성: focusDate=today.
- 전체 화면에서 생성: focusDate=null.
- 두 경우 모두 dueDate=null, priority=none, category=null.
- 제목만으로 저장 가능하며 성공 후 입력창을 비우고 연속 입력을 지원한다.
- 한글 IME 조합 중 Enter는 제출하지 않는다. 입력 조합 확정과 제출을 실제로 구분한다.

정렬:
- 오늘의 기한 초과: 기한이 오래 지난 순 → 높은 우선순위 → 먼저 생성한 순.
- 오늘의 나머지: 높은 우선순위 → 먼저 생성한 순.
- 전체: 오늘/기한 초과 → 미래 기한 → 나머지 미완료. 그룹 안은 높은 우선순위 → 먼저 생성한 순.
- 완료: 최근 완료 순. 동률에는 안정적인 기준을 둔다.

## 4. 날짜·저장·복구의 정확성

오늘 날짜는 브라우저의 getFullYear/getMonth/getDate로 계산한다. `toISOString().slice(0, 10)`를 오늘 날짜에 사용하지 않는다.

앱이 계속 열린 상태의 자정 변경, window focus, visibilitychange에서 날짜를 갱신한다. 날짜가 바뀌면 이전 focusDate 항목은 오늘에서 빠지지만 전체에 남고, 지난 기한은 기한 초과가 된다. 로컬 날짜 연산은 월말·연말과 일광절약시간에도 달력 날짜 기준으로 처리한다. 테스트에서 날짜를 제어할 수 있게 한다.

localStorage:
- 하나의 versioned key를 사용하고 초기 로드 완료 전 기본 빈 데이터를 덮어쓰지 않는다.
- 접근, 읽기, JSON 파싱, 스키마 검증, 쓰기의 실패를 처리한다.
- 저장 성공 후에만 `저장됨`을 표시한다.
- 쓰기 실패 시 현재 메모리의 변경은 유지하며 지속적인 안내를 표시한다:
  “변경 사항을 이 브라우저에 저장하지 못했습니다. 현재 탭에서는 사용할 수 있지만 새로고침하면 변경 내용이 사라질 수 있습니다.”
- 재시도 수단을 제공한다. 다음 쓰기가 실제로 성공하면 실패 상태를 해제한다.
- 손상된 JSON·지원하지 않는 버전을 빈 데이터로 조용히 덮어쓰지 않는다. 원본을 보존하고 복구 안내를 제공한다. 기존 데이터를 지우는 초기화가 필요하면 사용자의 명시적인 확인을 받는 UI를 둔다.
- 서버 백업·다른 기기 동기화·다중 탭 동시 편집을 보장한다고 표현하지 않는다.

완료:
- completedAt을 기록하고 미완료 목록에서 이동시킨다.
- `할 일을 완료했습니다. 실행 취소` 피드백을 제공한다.
- 실행 취소가 사라진 뒤에도 완료 영역에서 미완료로 복원할 수 있다.

삭제:
- 상세 편집의 보조 행동으로 배치한다.
- 삭제 직후 `할 일을 삭제했습니다. 실행 취소`를 약 8초 제공한다.
- 삭제 취소는 id, 제목, 기한, focusDate, 우선순위, 분류, 완료 여부, isDemo를 보존하여 복구한다.
- 최소 범위에서는 가장 최근 완료/삭제 한 건의 실행 취소를 지원한다. 새 행동으로 교체될 때 이전 알림의 타이머가 새 복구 동작을 지우지 않게 처리한다.
- 실행 취소 중 다른 항목을 편집해도 그 변경을 되돌리지 않도록 해당 항목에만 복구를 적용한다.
- 알림에 마우스를 올리거나 키보드 포커스가 있는 동안에는 만료를 멈춘다.
- 삭제 취소의 시간 제한과 새 행동 시 교체 규칙을 문서에 기록한다.

## 5. UX와 UI

목표는 차분한 생산성 앱이다. 리서치의 quiet productivity 방향을 유지하면서 타이포그래피, 간격, 정보 위계, 상태 피드백, 조작감으로 완성도를 높여라.

- 배경 #F8FAFC, 표면 #FFFFFF, 본문 #111827, 보조 #475569, 강조 #4F46E5, 포커스 #4338CA, 위험 #B91C1C를 기본 토큰으로 사용한다.
- 4/8/12/16/24/32px 간격 체계, 8~16px 모서리, 시스템 폰트, 본문·입력·할 일 제목 약 16px.
- 실제 배경과 상호작용 상태에서 텍스트 대비를 확인한다.
- 강한 그라데이션, 유리 효과, 큰 히어로, 장식용 대시보드, 불필요한 통계 카드, 과도한 애니메이션은 넣지 않는다.
- 특정 경쟁 앱의 브랜드·화면을 복제하지 않는다.
- 할 일 행에는 체크박스, 제목, 필요한 메타데이터만 표시한다. 없는 속성의 빈 칩을 만들지 않는다.
- 제목은 데스크톱 2줄, 모바일 2~3줄로 제한해 표시할 수 있지만 편집에서 전체를 확인해야 한다.
- 날짜·기한 초과·우선순위는 색과 함께 텍스트로 표현한다.
- 제목 영역의 편집과 체크박스의 완료가 서로 잘못 실행되지 않게 한다.

데스크톱 약 900px 이상:
220~240px 사이드바, 최대 760~820px 작업 목록, 상단 제목·날짜·검색, 지속적으로 보이는 빠른 입력창, 우측 상세 drawer. 공간이 부족하면 drawer를 overlay로 표시한다.

모바일:
사이드바 대신 오늘/전체 하단 탐색, 명확한 `+ 할 일 추가`, 상세 편집 bottom sheet. 같은 편집 로직을 공유하되 장치에 맞게 배치한다. 320px 화면, 긴 한글·공백 없는 문자열, 화면 키보드, safe-area, 하단 탐색과 알림의 겹침을 고려한다. 핵심 터치 영역은 약 44×44px 이상 확보한다.

편집기는 제목, 오늘 집중 여부, 기한 설정·해제, 우선순위, 분류, 삭제를 제공한다. 편집 내용은 `저장`으로 적용하고 `취소/Escape`는 미적용 초안을 버린다. 제목이 비면 저장을 막고 입력 오류를 표시한다. 날짜만 있는 기한에 시간 선택기를 붙이지 않는다.

접근성:
semantic HTML과 native button/input/checkbox를 우선한다. 모든 입력에 label, 아이콘 버튼에 접근 가능한 이름, 명확한 focus ring을 제공한다. 키보드로 추가→편집→저장→완료→실행 취소가 가능해야 한다.
모달 편집기에는 적절한 dialog 의미, 포커스 이동·유지·닫힌 후 복귀를 제공한다. 완료·삭제로 행이 사라지면 포커스가 문서 처음으로 유실되지 않게 한다.
상태 메시지는 적절한 live region으로 전달하고, hover에만 핵심 행동을 숨기지 않는다. prefers-reduced-motion을 반영한다.
선택적으로 N은 새 입력, /는 검색으로 이동하게 하되 입력 요소·contenteditable·IME 조합·조합키 사용 중에는 가로채지 않는다.

빈 상태:
- 최초 빈 화면: “해야 할 일을 하나 적어보세요” + 첫 할 일 추가 + 보조 버튼 “예시로 둘러보기”.
- 오늘만 비어 있음: “오늘은 비어 있습니다” + 전체 할 일에서 선택하거나 새로 추가하라는 안내.
- 검색 결과 없음: 검색어와 일치하는 할 일이 없다는 안내 + 검색 지우기.
- 오류는 한국어로 원인과 다음 행동을 짧게 안내한다. 긴 온보딩은 만들지 않는다.

## 6. 예시 데이터와 시연

예시 데이터는 자동 삽입하지 않는다. 사용자가 `예시로 둘러보기`를 선택할 때만 현재 날짜 기준으로 5개 정도 추가한다.

예: 어제 기한의 택배 반품 접수, 오늘 기한의 발표 자료 확인, 오늘 집중할 세탁소 방문, 미래 기한의 카드 명세서 확인, 기한 없는 주말 장보기.

- 모두 isDemo=true로 표시한다.
- 재실행해 중복 삽입되지 않게 한다.
- 기존 사용자 데이터를 덮어쓰지 않는다.
- `예시 데이터 제거`는 isDemo=true만 제거한다. 사용자 항목은 유지한다.
- 예시 관리와 앱 정보는 작은 보조 메뉴에 둔다. 별도 최상위 화면으로 확장하지 않는다.
- 테스트용 200개 항목은 일반 사용 화면에 자동 삽입하지 않는다.

2~3분 시연 절차를 `docs/demo-script.md`에 작성한다:
빠른 입력 → 전체에서 오늘에 추가 → 내일 기한인데 오늘에 집중하는 항목 → 완료와 실행 취소 → 수정·새로고침 유지 → 모바일 편집 → GitHub의 설계 근거·AI 활용·검증 기록.

## 7. 실제 검증과 수정

완성 판단 전에 실행 가능한 검증을 수행하라. 적절한 도구가 있다면 도메인·저장 단위 테스트와 브라우저 E2E를 사용한다. 테스트 개수보다 제품 규칙을 검증하는 데 집중한다.

반드시 확인할 항목:
1. 오늘/전체에서 생성하는 기본값과 보기 포함 규칙.
2. focusDate와 dueDate의 독립성, 기한 때문에 오늘에 남는 항목의 안내.
3. 빈 제목, 200자 제목, 공백 없는 긴 문자열, 한글 IME Enter.
4. 제목·속성 수정과 새로고침 후 유지.
5. 완료·복원·삭제 취소, 연속 행동과 타이머, 다른 항목 변경 보존.
6. 자정·focus·visibilitychange의 날짜 갱신과 월말·연말.
7. localStorage 접근·쓰기 실패, 잘못된 JSON·스키마·버전, 원본의 비의도적 덮어쓰기 방지.
8. 검색, 결과 없음, 예시 중복 방지와 사용자 항목 보존.
9. 100~200개 항목의 기본 조작·검색·스크롤.
10. 1440×900, 1366×768, 390×844, 320px 폭에서 레이아웃·가로 넘침·편집기·하단 UI.
11. 키보드 흐름, 포커스 복귀, 접근 가능한 이름, 대비와 reduced-motion.
12. TypeScript, lint, 테스트, production build, 빌드 결과의 실제 로딩과 자산 경로.

브라우저에서 실제 화면을 열어 데스크톱·모바일의 전체 구성과 편집 상태를 시각적으로 확인하고 문제를 수정하라. 에뮬레이션을 실제 스마트폰 테스트로 기록하지 않는다. 브라우저·의존성 설치 등 환경 제약이 있으면 가능한 검증을 끝내고 미실행 항목과 이유를 기록한다.

`docs/validation.md`에는 환경, 명령, 확인한 행동, 기대 결과, 실제 결과, 증거, 남은 문제를 남긴다. PASS/FAIL/NOT_RUN을 구분하고, 수행하지 않은 테스트·사용자 연구·접근성 준수·성능을 성공했다고 쓰지 않는다. 실패한 테스트를 지우거나 기대 결과를 약화하여 통과시키지 않는다.

## 8. 문서와 AI 활용 증거

프로젝트에 다음을 포함한다. 문서 내용은 실제 구현·작업과 일치해야 한다.

- README.md: 제품 설명, 대표 화면, 기능, 실행·빌드·검증 방법, 저장 방식, 설계 차별점, 제한, AI 활용, 리서치 연결.
- docs/research.md: 리서치의 핵심 근거와 조사 한계. 원문이 제공되었다면 수정 없이 docs/references/에 보존한다.
- docs/product-spec.md: 최종 범위, 데이터, 날짜, 저장, 보기와 상호작용 규칙.
- docs/decisions.md: 조사 발견 → 설계 결정 → 이유·절충점.
- docs/validation.md: 실제 검증과 남은 제한.
- docs/demo-script.md: 시연 절차.
- docs/ai-workflow.md 및 docs/ai-prompts/: 실제 사용한 주요 요청·검토, 발견한 문제, 반영·수정·거절한 내용과 이유.
- docs/screenshots/: 실제 앱에서 촬영한 데스크톱·모바일 대표 화면. 가능하면 편집 상태도 포함.

AI 검토는 저장·날짜·복구 → UX·모바일 → 접근성·문서의 관점으로 수행하고 결과와 수정 내용을 기록한다. 별도 모델이나 사람이 검토하지 않았다면 그렇게 주장하지 않는다. 이 프롬프트를 최초 구현 요청으로 보존한다.

문서는 한국어를 기본으로 하고 README는 제품부터 보여준다. 공개 자료의 조사 결과와 설계 가설, 실제 앱 검증을 구분한다. 리서치에 실제 URL이 없으면 출처 제목을 보존하고 필요한 공식 링크만 확인하여 추가한다. 내부 인용 토큰을 임의의 URL로 변환하지 않는다.

제한에는 로컬 데이터 삭제 가능성, 서버 백업·동기화 없음, 다중 탭 동시 편집 미보장, 삭제 실행 취소 제한, 실제 사용자 연구 미실시를 명시한다. 실행하지 않은 환경은 검증 완료로 쓰지 않는다.

## 9. GitHub 제출과 배포 준비

프로젝트 전체와 문서를 포함하되 node_modules, dist, 로컬 테스트 부산물, 비밀정보는 제외한다. 기존 01/02 등 실습 폴더가 있으면 보존한다.

- 실제 완료된 작업 단위로 커밋한다: 설계 근거 → 데이터·저장 → 핵심 흐름 → 반응형 → 결함 수정·검증 → 문서·스크린샷.
- 기존 변경을 무관하게 커밋하거나 사후에 개발 이력을 꾸미지 않는다.
- 사용자 Git identity를 임의로 만들지 않는다. force push와 기존 이력 재작성은 하지 않는다.
- 이 과제용으로 연결된 저장소와 인증이 확인되면 정상적인 commit/push로 공유를 완료한다.
- 대상 저장소·공개 범위가 불명확하거나 권한이 없으면 로컬 구현·검증·제출 준비를 먼저 끝내고 필요한 정보만 요청한다. 새 공개 저장소를 임의로 만들지 않는다.
- GitHub Pages용 설정과 배포 절차를 준비한다. 실제 게시가 요청되거나 이미 허용된 환경이면 배포 후 URL과 자산 로딩을 확인한다.
- 저장소 URL과 Live Demo URL은 실제 확인된 것만 적는다. 배포 준비를 배포 완료로 표현하지 않는다.

## 10. 실행 원칙과 최종 보고

처음에 짧은 실행 계획을 제시한 뒤 바로 구현하라. 계획만 제시하고 멈추지 않는다. 제품 범위 안의 세부 선택은 스스로 결정한다. 진행 중에는 중요한 발견과 다음 작업을 짧게 알리고, 기능 확장보다 결함 수정과 검증을 우선한다.

작동하지 않는 버튼, TODO로 남은 핵심 기능, 가짜 저장 상태, 구현하지 않은 기능을 보여주는 목업으로 끝내지 않는다. 개발 서버 실행만으로 완료를 선언하지 말고 production build까지 확인한다.

최종 보고에는 다음만 명확히 제시하라:
- 완성한 제품과 핵심 차별점.
- 실행 방법과 확인 가능한 위치.
- 실제 테스트 결과와 중요한 제한.
- Git 커밋·push 상태, 확인된 저장소·배포 URL.
- 환경 제약 또는 사용자에게 남은 최소 작업.

이제 현재 작업 공간을 확인하고 Focusday 구현을 시작하라.

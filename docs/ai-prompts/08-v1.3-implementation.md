# Focusday v1.3 — 노션 작업 화면을 참고한 UI 전면 교체

현재 작업 폴더의 Focusday 앱을 아래 확정된 디자인에 따라 구현·검증·문서화하라. 이번 요청은 디자인 제안만 작성하는 일이 아니라 실제 앱의 UI를 전면 교체하는 작업이다. 계획이나 목업 작성에서 멈추지 말고 실행 가능한 결과를 완성하라.

저장소: https://github.com/gsj118/focusday
공개 사이트: https://gsj118.github.io/focusday/

기준으로 확인한 버전은 v1.2.0이다. 작업 시작 시 실제 체크아웃과 원격 상태를 확인하고, 더 최신 변경이 있다면 그 변경을 보존한 상태에서 작업하라. 기존 사용자 변경을 덮어쓰거나 작업 폴더를 초기화하지 마라. 필요한 작업 위치와 브랜치는 직접 확인하라.

## 1. 확정된 목표

Focusday를 “노션 안에 만든 잘 정돈된 개인용 할 일 페이지”처럼 느껴지도록 바꾼다.

추상적으로 노션에서 영감만 받는 수준이 아니라, 노션의 실제 작업 화면에서 나타나는 사이드바, 페이지 제목, 목록 밀도, 타이포그래피, 속성 태그, 얇은 구분선, 선택·호버·포커스 표현을 충실하게 참고한다. 시각 표현의 주 참조는 노션 하나로 통일한다.

전체 구조는 왼쪽 사이드바와 오른쪽 작업 본문을 사용하는 정돈된 워크스페이스다. Focusday의 이름과 제품 목적, 기존 기능과 데이터는 유지한다. 목표는 깔끔한 홈페이지가 아니라 매일 빠르게 입력하고 처리할 수 있는 실제 작업 앱이다.

## 2. 참조 자료와 사용 원칙

다음 자료를 직접 확인하고 설계 근거를 기록하라.

- https://getdesign.md/notion/design-md
- https://getdesign.md/design-md/notion/preview
- https://github.com/VoltAgent/awesome-design-md

getdesign.md의 노션 분석은 제3자의 해석이며, 마케팅 홈페이지용 표현이 섞여 있다. 실제 노션 작업 화면의 공식 예시를 함께 대조하라. 큰 홍보용 제목, 요금제 카드, 캡슐 CTA, 장식 일러스트를 할 일 앱으로 그대로 옮기지 마라.

노션의 이름·로고·독점 이미지·전용 폰트 자산을 가져오지 않는다. 제품명은 Focusday이며, 아이콘은 기존 Icon 컴포넌트를 우선 활용한다. 여러 회사의 스타일을 임의로 혼합하거나 UI 템플릿의 기본 모습으로 대체하지 마라.

자료 접근이 불가능하면 가능한 자료와 현재 코드로 진행하되 접근하지 못한 자료를 확인했다고 기록하지 마라. DESIGN.md 확보를 위해 새 CLI나 패키지를 설치할 필요는 없다.

## 4. 시각 디자인 결정

밝은 테마를 기준으로 완성한다. 이번 범위에서 테마 선택 기능은 추가하지 않는다.

아래 값은 Focusday에 적용할 초기 디자인 값이며, 노션의 공식 토큰을 추출한 값이라고 주장하지 마라. 실제 렌더링과 접근성을 검토해 필요한 만큼 미세 조정한다.

| 요소 | 기준 |
| --- | --- |
| 본문 배경 | #FFFFFF |
| 사이드바·조용한 안내 배경 | #F7F7F5 |
| 기본 글자 | #37352F |
| 보조 글자 | #6B6B65, 실제 대비 확인 |
| 구분선 | #E9E9E7 |
| 선택·호버 표면 | #EFEFED |
| 주요 조작·집중 강조 | #2383E2 계열, 흰 글자 버튼은 대비에 맞게 더 어둡게 조정 |
| 경고 | 차분한 적갈색 계열과 명시적인 텍스트 |
| 모서리 | 작은 컨트롤 4–6px, 패널 8px 안팎 |
| 그림자 | 일반 목록에는 없음, 떠 있는 메뉴·패널에만 최소한 |

색상·간격·글자 크기·모서리·패널 폭을 CSS 토큰으로 정의하고 모든 화면에 적용하라. 값이 컴포넌트마다 흩어지지 않게 한다.

폰트는 외부 로딩 없이 시스템 sans-serif와 한글 fallback을 사용한다. 본문은 14–16px, 보조 정보는 12–13px를 기준으로 한다. 제목은 데스크톱 34–36px, 모바일 28–30px 정도로 명확한 위계를 만든다. 작은 글자를 과하게 촘촘하게 배치하지 않는다. 한글에 영문용 강한 음수 자간을 일괄 적용하지 마라.

## 5. 레이아웃과 화면 구성

### 데스크톱

- 왼쪽 사이드바는 약 220–240px로 구성한다. 작은 Focusday 표시, 검색 진입, 오늘/전체 할 일 메뉴와 실제 개수, 하단 앱 정보·예시·백업 진입을 배치한다.
- 메뉴는 작은 아이콘과 글자를 함께 사용하고, 선택 상태는 회색 표면과 적절한 글자 강조로 나타낸다. 사이드바 공간을 채우려고 존재하지 않는 메뉴를 만들지 않는다.
- 본문 상단에는 간단한 현재 위치와 실제 저장 상태를 배치한다. 공유·팀·계정 등 작동하지 않는 버튼을 추가하지 마라.
- 본문은 좁게 떠 있는 카드가 아니라 작업 페이지처럼 구성한다. 큰 화면에서는 약 880–1040px의 읽기 좋은 작업 폭을 확보하고, 노트북에서는 남은 공간을 합리적으로 활용한다.
- 순서는 페이지 제목과 날짜 → 짧은 설명 → 오늘 집중 요약 및 계획 진입 → 검색과 목록 도구 → 빠른 입력 → 목록 그룹이다.
- 화면 제목은 “오늘” 또는 “전체 할 일”로 유지한다. 과도하게 큰 홍보 문장이나 인사말은 사용하지 않는다.
- 본문 전체를 반복되는 둥근 카드로 감싸지 않는다. 제목·간격·얇은 구분선으로 영역을 구분한다.

### 빠른 입력

- 입력창은 목록 위에 둔다. 긴 목록을 스크롤한 뒤에야 새 일을 추가할 수 있는 구조를 만들지 마라.
- 단순한 입력 행으로 표현하되 입력 위치와 추가 버튼은 명확히 식별되어야 한다.
- Enter 또는 추가 버튼으로 즉시 추가하고, 성공하면 입력을 비운 뒤 같은 입력창에 포커스를 유지한다.
- 현재 보기별 추가 의미를 유지한다. 오늘에서 추가하면 오늘 집중, 전체에서 추가하면 전체에 담긴다.
- 입력 안내와 오류는 짧고 명확하게 제공한다. 장식용 단축키나 구현하지 않은 키 명령을 표시하지 않는다.
- 기존 sticky 동작을 조정한다면 작은 화면·확대·키보드 표시에서 내용과 포커스를 가리지 않는지 검증한다.

## 6. 할 일 목록 — 정보 손실 없는 노션식 표현

보기에는 노션의 목록·데이터베이스를 연상시키되, 기존 기능을 별도의 복잡한 데이터베이스 기능으로 확장하지 않는다.

- 일반 제목 한 줄과 간단한 속성일 때 데스크톱 행 높이는 약 52–64px를 기준으로 한다. 긴 제목이나 많은 속성이 있으면 자연스럽게 높아져야 한다.
- 체크박스 → 제목과 필요한 메타정보 → 집중 전환 조작 순서로 배치한다.
- 제목 클릭은 기존 상세 편집을 연다. 체크박스·집중 전환을 눌렀을 때 상세 편집이 함께 열리지 않게 한다.
- 기한, 우선순위, 분류, 예시 여부가 설정되어 있다면 모두 확인 가능해야 한다. 노션 느낌을 내기 위해 우선순위나 기한을 숨기지 마라.
- 큰 화면에서는 속성을 정렬하고, 좁은 화면에서는 제목 아래로 자연스럽게 재배치한다. 의미 없는 빈 열과 고정 폭 표로 공간을 낭비하지 않는다.
- 긴 한글·영문·공백 없는 제목과 분류를 처리한다. 데스크톱은 제목 최대 2줄, 모바일은 3줄 안팎을 기본으로 하며 전체 제목은 상세 편집에서 접근할 수 있어야 한다. CSS 말줄임과 접근 가능한 이름을 함께 확인한다.
- 현재 grouping과 정렬 로직을 유지한다. 오늘에는 기한 초과/오늘, 전체에는 미완료 및 완료 영역을 표시한다.
- 체크박스는 차분한 사각형, 분류는 작은 직사각형 태그, 기한 초과는 적갈색 텍스트로 표현한다. 색만으로 상태를 전달하지 않는다.

“오늘 집중”의 상태와 전환 조작은 구별하라. 작은 읽기 전용 “오늘 집중” 표시는 상태이며, 별도의 조작은 실제 동작을 나타내는 “집중하기” 또는 “집중 해제”이다. 같은 정보를 반복해서 시각적으로 과밀하게 만들지 않되, 현재 상태와 다음 동작을 모두 이해할 수 있어야 한다. 전환 버튼에는 작업별 접근 가능한 이름과 aria-pressed를 제공한다. 호버해야만 발견되는 필수 조작을 만들지 마라.

## 7. 계획·상세 편집·백업·보조 화면

### 오늘 계획하기

- 본문에는 작은 아이콘, 실제 집중/기한 개수, 계획 버튼이 있는 차분한 안내 블록을 둔다. 어제 미완료가 있으면 사실에 맞게 표시한다.
- 계획 버튼을 누르면 기존 PlanPanel의 기능을 유지한 사이드패널을 연다. 데스크톱에서 항상 세 번째 열을 점유하지 않는다.
- 모바일에서는 기존 접근 가능한 sheet 방식으로 재배치한다. 화면·가상 키보드 크기에 맞게 패널과 내부 내용을 관리한다.
- 기한 초과·오늘 기한·어제 선택·높은 우선순위 후보와 선택 이유를 유지한다. 수치나 후보를 고정된 예시 문구로 만들지 마라.
- 후보에서 집중 선택은 바로 적용된다. 상세 편집의 저장/취소 방식과 혼동되지 않도록 짧은 설명을 유지한다.
- 후보 없음, 선택 완료, 집중 해제 후 기한 때문에 오늘에 남는 상태, 저장 오류도 같은 디자인 규칙으로 다룬다.

### 상세 편집

- 기존 TaskEditor의 초안·저장·취소·삭제 의미를 유지한다. 이번 작업에서 자동 저장 편집기로 바꾸지 않는다.
- 제목을 시각적으로 가장 중요하게 두고, 오늘 집중·기한·우선순위·분류를 노션 속성처럼 라벨과 값이 정렬되는 형태로 구성한다.
- native input, textarea, select를 우선 활용한다. 값이 바뀌어도 저장 또는 취소가 명확해야 한다.
- 데스크톱은 오른쪽 패널, 모바일은 sheet로 구성한다. 하단 저장·취소·삭제는 내용이나 키보드에 가려지지 않아야 한다.
- 제목 textarea의 Enter는 줄바꿈, 취소/Escape는 초안 폐기라는 기존 의미를 유지한다.

### 백업·복원 및 기타 상태

- DataPanel, 가져오기 미리보기, 합치기/전체 교체 선택, 교체 확인, 성공/실패 안내, UndoToast, 저장 보호 안내, 빈 상태, 검색 결과 없음, 완료 목록, 앱 메뉴를 함께 재디자인한다.
- 백업 메뉴를 실제로 연결한다. 시각적으로만 보이는 비활성 텍스트나 가짜 버튼으로 대체하지 않는다.
- 사용자 데이터가 없는 최초 진입은 간단한 제목·설명·행동으로 구성한다. 큰 점선 카드와 과도한 장식은 제거한다.
- 예시 데이터는 사용자가 선택할 때만 제공하고 실제 데이터와 구분한다.

## 8. 기능과 데이터 보존 조건

아래 조건을 먼저 이해하고 UI 변경 전후로 보존하라.

1. 오늘 집중과 기한은 서로 다른 속성이다. 내일 기한인 일을 오늘 집중으로 선택할 수 있다.
2. 집중 해제는 기한을 변경하지 않는다. 오늘/과거 기한 때문에 오늘에 남는 경우 그 이유를 알려준다.
3. 어제의 미완료를 자동 이월하지 않는다. 직접 이어갈 때 기존 id와 기한을 유지한다.
4. 저장 키 focusday:v1과 데이터 version:1을 유지한다. UI 버전 변경은 데이터 마이그레이션의 이유가 아니다.
5. 기존 할 일의 모든 속성, 완료 상태, 예시 구분, 검색·정렬 의미를 보존한다.
6. 초기 읽기, 손상 원본 보호, 저장 실패 중 메모리 변경, 복원 실패 시 적용 전 상태 유지 등 저장 보호 동작을 보존한다.
7. JSON 백업은 전체 데이터를 대상으로 한다. compact 내보내기와 가져오기의 동일 10MiB UTF-8 한도, 미리보기, 합치기, 교체 확인, 중복 id 처리와 실패 보호를 유지한다.
8. 완료·삭제 실행 취소, hover/포커스 중 타이머 정지, 완료 영역에서 복원, 복원 성공 후 오래된 편집·검색·undo 정리 등 기존 동작을 보존한다.
9. 빠른 입력 및 상세 분류 입력의 한글 IME 조합 Enter 보호를 유지한다. 합성 이벤트 테스트를 실제 OS IME 시험이라고 기록하지 않는다.
10. 로컬 날짜·자정 변경 처리와 키보드 단축키를 유지한다. 단축키가 입력 중이나 modal 안에서 잘못 실행되지 않아야 한다.

UI 리팩터링은 허용한다. 데이터·백업·날짜 로직은 이번 디자인에 꼭 필요한 경우가 아니라면 수정하지 않는다. 새 분류 필터, 보드, 달력, 드래그 정렬, AI 추천, 협업, 통계, 로그인, 동기화, 테마 전환 등 기능 확장은 이번 범위에 넣지 마라.

## 9. 반응형과 접근성

- 1440×900, 1366×768, 1024×768, 768×1024, 390×844, 320×568에서 확인한다. 숫자는 검증 목표이며 임의의 breakpoint를 강제하는 것은 아니다.
- 공간이 부족하면 데스크톱 사이드바를 숨기거나 접고 기존 오늘/전체 하단 내비게이션을 재디자인한다. 모바일에서 두 보기와 백업·계획·편집에 모두 접근할 수 있어야 한다.
- 작은 체크박스·아이콘의 보이는 크기와 조작 영역은 분리한다. 터치 조작 영역은 약 44×44px를 확보하되 목표 영역끼리 겹치지 않는다.
- 모바일 입력은 16px 이상을 사용한다. safe-area, 가상 키보드, 패널 내부 스크롤, 하단 내비게이션과 toast의 겹침을 확인한다.
- 200% 확대/reflow에서도 필수 내용·조작·포커스가 가려지지 않고 가로 스크롤 없이 사용할 수 있어야 한다.
- keyboard-only로 입력, 검색, 메뉴 이동, 완료, 집중 전환, 패널 열기·닫기, 저장·취소, 복원 미리보기를 사용할 수 있어야 한다.
- modal의 초점 관리, 닫은 뒤 초점 복귀, Escape, 포커스 표시, 스크린 리더용 이름과 상태 안내를 유지한다.
- 일반 텍스트 4.5:1, 큰 텍스트 및 필요한 UI 경계·상태 표시 3:1의 대비 기준을 실제 사용 조합별로 확인한다. 구분선 전체에 동일 기준을 기계적으로 적용하지 말고 의미 전달에 필요한 경계인지 판단한다.

## 10. 구현·검수 방식

1. 현재 코드·문서·baseline을 확인하고 주요 변경 범위를 짧게 정리한다.
2. 프로젝트 루트에 Focusday 전용 DESIGN.md를 작성한다. 참조와 적용 결정, CSS 토큰, 타이포그래피, 레이아웃, 컴포넌트 상태, 반응형·접근성 기준을 포함한다.
3. 목록 하나만 바꾸고 끝내지 말고 관련 화면과 상태를 같은 규칙으로 구현한다.
4. 실제 앱을 실행해 desktop/mobile 화면을 캡처하고 직접 검수한다. 코드만 보고 디자인 검수를 완료했다고 하지 않는다.
5. 내용의 위계, 노션과의 시각적 유사성, 긴 데이터의 흐름, 상태의 이해 가능성, 조작 편의성, 화면 간 일관성을 검토해 문제를 수정한다.
6. 타입·lint·단위·날짜·빌드와 기존 E2E를 실행한다. 실제 package.json 명령을 기준으로 하되 확인 당시 pnpm check와 pnpm test:e2e를 사용한다.
7. UI 구조 변경으로 locator가 바뀌면 테스트를 의미 기반으로 갱신한다. 실패를 없애려고 테스트를 삭제·skip하거나 검증을 약화하지 마라. 기능 의미가 바뀐 결과를 단순 locator 변경으로 숨기지 마라.
8. 새 테스트는 변경한 상호작용과 위험이 있는 회귀를 검증하는 데 필요한 만큼만 추가한다. CSS 값과 구현을 그대로 반복하는 테스트를 대량 추가하지 않는다.
9. production build와 Pages의 /focusday/ 경로에서 자산·동작을 확인한다. 기존 Playwright 설정과 서버 재사용 방식을 따르고 실제 실행 명령·환경·결과를 기록한다.

최소한 다음 실제 상태를 검수한다.

- 빈 앱의 첫 입력, Enter 연속 입력, 공백 입력 오류, 긴 제목·분류
- 오늘/전체 전환, 제목·분류 검색, 검색 결과 없음, 완료 항목 표시·복원
- 미래 기한+오늘 집중, 오늘 기한+집중 해제, 기한 초과, 기한 없음
- 계획 후보 선택·해제, 어제 이어가기, 후보 없음
- 상세 편집의 저장·취소·Escape·제목 줄바꿈·조합 Enter
- 완료·삭제·undo와 포커스 복귀
- 백업 다운로드·자체 파일 재가져오기·미리보기·합치기·전체 교체·취소
- 저장 오류·손상 원본 보호·복원 실패
- 320px 패널, 작은 높이, 확대, keyboard-only, 키보드 표시 상황

실제 사용자 목록이나 공개 사이트의 기존 데이터를 검증 fixture로 덮어쓰지 않는다. 브라우저 검증과 촬영은 격리된 context에서 합성 데이터를 사용한다. 시험용 데이터와 고정 날짜를 앱의 실제 초기 상태에 넣지 마라. 물리 기기·OS IME·스크린 리더 등 실행하지 않은 시험은 미실행으로 기록한다.

## 11. 버전·문서·개발 기록

- v1.2.0 기준 작업이라면 앱 버전은 v1.3.0으로 업데이트하고 저장 형식은 유지한다. 이미 다른 버전 작업이 진행 중이면 충돌 없이 맞는 다음 버전을 결정하고 근거를 기록한다.
- DESIGN.md, docs/V1_3_UI_REDESIGN.md, README.md, CHANGELOG.md와 영향을 받는 검증·배포 문서를 갱신한다.
- 재디자인 문서에는 기존 문제, 노션 참조 방식, 정보 손실을 막은 결정, 실제 변경 전후 화면, 회귀 검증, 한계와 미실행 항목을 간결하게 정리한다.
- 현재 체크아웃에서 촬영한 before와 구현 후 after를 docs/screenshots/v1.3/ 아래 구분해 보관한다. 과거 화면은 삭제하거나 최신 before로 가장하지 않는다.
- 실제 앱 스크린샷만 사용한다. 생성 이미지나 목업을 구현 결과로 제시하지 않는다.
- 기존 태그·버전 문서·v1.2 시험 증거·개발 이력을 보존한다. 개발 과정은 실제 변경 단위로 커밋하고 AI 활용 기록에 이번 요청과 설계·검증 과정을 남긴다. 테스트가 끝난 것처럼 날짜·횟수·PASS를 만들어 쓰지 마라.

## 12. GitHub 반영과 완료 조건

검증과 문서화가 완료되면 기존 프로젝트 제출 방식에 따라 의미 있는 커밋을 남기고, 연결된 원격 저장소에 정상적인 방식으로 push하라. 다른 사람의 변경을 덮는 force push, 이력 재작성, 실패한 검증을 숨기는 커밋은 하지 않는다. 사용자 변경을 함께 묶지 마라.

기존 Pages workflow와 배포 정책을 확인하고, 정상적인 main 반영 조건이 충족되면 기존 방식으로 배포한다. 확인 당시 Pages는 main의 수동 workflow이므로 push만으로 배포 완료라고 간주하지 마라. PR 검토가 필요한 저장소면 그 절차를 유지하고, 권한·필수 검토가 막히면 우회하지 않는다. 배포한 경우 공개 사이트에서 버전·자산·핵심 조작을 다시 검증한다. 원격 반영이나 배포가 불가능해도 로컬 구현·검증·문서화는 끝까지 완료하고 실제로 완료된 범위를 구분해서 보고한다.

다음 조건을 모두 충족할 때 작업 완료로 본다.

- 실제 화면이 노션을 알아볼 수 있을 만큼 일관된 작업 UI로 바뀌었다.
- 빠른 입력·목록·계획·편집·백업·오류·빈 상태·모바일이 같은 디자인 규칙을 따른다.
- 기한·우선순위 등 정보가 사라지지 않았고 기존 기능·저장 데이터의 의미를 보존했다.
- 데스크톱과 모바일 화면을 실제 렌더링으로 검수하고 발견한 문제를 수정했다.
- 필요한 검증을 통과했거나, 환경상 미실행과 남은 실패를 사실대로 명시했다.
- 변경 전후 화면, 설계 근거, 검증 결과와 실제 개발 기록이 남아 있다.

최종 보고에는 완료한 UI 변화, 데이터·기능 보존 결과, 실제 검증 결과와 한계, 주요 문서·화면 경로, 커밋/PR/배포 상태를 간결하게 제시하라. 다시 디자인 선택지를 묻거나 제안만 반복하지 말고, 이 확정된 방향을 기준으로 필요한 세부 결정을 내려 완성하라.
